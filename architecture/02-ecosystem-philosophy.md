# Ecosystem Philosophy

## The Ecosystem Philosophy

The Aggrega architecture is guided by core design principles that balance flexibility with predictability. By maintaining clear boundaries and standardized contracts, a fundamentally generic compiler can seamlessly orchestrate everything from standard cloud-native infrastructure to highly specialized AI intelligence.

### 1. **Core Mechanics: The Physics of the Architecture**

* **Separation of Concerns (Conway's Law):** Developers must never write physical infrastructure code, and Ops must never hardcode application logic. The architecture is strictly divided into Domain-Driven boundaries.
* **Late Binding (Dependency Inversion):** Developers request abstract Interfaces (e.g., `type: enterprise-agent`), not specific Implementations (e.g., `helm-chart-v2`). The Manifest resolves the interface to the correct implementation at compile time, allowing true multi-target deployments from a single source file.
* **AOT Purity (No Live Cloud Fetching):** The compiler is mathematically blind to the live cloud. It never authenticates with infrastructure APIs or fetches live IP addresses during compilation. It operates entirely on *Control Inversion*, mapping deterministic pointers and passing abstract Injection Contracts ahead of time so the runtime environment can safely resolve the final physical connections.

### 2. **The Developer Experience: Intent & Abstraction**

* **Semantic Developer Experience (The 5-Keyword Map Standard):** To prevent cognitive friction, developers use exactly five universally understood keywords within a Map-based YAML topology:
  1. `parameters`: The global environment contract (e.g., passing dynamic disk sizes).
  2. `values`: The core cognitive/business logic payload (Developer Owned).
  3. `uses`: The explicitly declared network edges and dependencies (Developer Owned).
  4. `infra`: The physical footprint and mechanical sizing (Ops Owned, banned from the Aggregate).
  5. `inject`: The strict delivery contract mapping local variables to target, provides keys (`env`, `file`, `arg`). This mechanism is extensible.
* **Target-Agnostic Terminology:** To prevent underlying infrastructure realities (like the Kubernetes term `namespace`) from bleeding into the developer experience, the platform utilizes universal concepts like `boundaries`.
* **Explicit Intent & The "Loud Guardrail" (No Ghost Infrastructure):** The compiler must never invent compute or features that the developer did not explicitly declare. Using a policy engine to silently inject a security proxy creates "Ghost Infrastructure"—when it breaks, the developer spends weeks debugging a proxy that doesn't exist in their YAML. Instead of silently mutating the architecture, Wasm policy plugins act strictly as **Loud Guardrails**. If a topology violates security, the compiler halts the build and returns a highly specific error (e.g., *"Error: PII data flowing to Public Network. You must explicitly attach the `core/data-masking` feature"*), forcing the developer to fix their own Single Source of Truth.

### 3. **The Unopinionated Engine: Processing & Orchestration**

* **Programmable Policies (The Unopinionated Engine):** The core Go compiler is a "dumb," calculating mechanism. It parses YAML, traverses graphs, and evaluates label intersections. The actual "intelligence" (e.g., enforcing that restricted data must pass through a masking proxy) is programmed dynamically by the enterprise using pluggable WebAssembly (Wasm) sockets for Abstract Syntax Tree (AST) mutations—altering the parsed, in-memory representation of the configuration—and policy validation.
* **Schema Agnosticism (open source dictionary):** The core compiler is mathematically blind to physical execution layers. It does not possess hardcoded schemas for Helm, Terraform, or Docker Compose. Instead, the `source` block of an Ops Recipe is an open dictionary whose keys are provider-defined and surface to the Recipe's templates as `.source.*`. The design direction is that each Provider's Wasm socket defines and validates its own source shape — so enterprises can introduce new infrastructure tools without waiting for core schema updates; that per-provider Wasm source validation is not yet implemented. Today the core resolves a *fetched* source by a built-in `{ kind, url, version }` form (kinds: `helm-oci-chart`, `helm-https-chart`, `compose-https-fragment`), which already decouples the compiler from the cloud languages it manipulates. See the Recipe `source` reference for the current fetch model and the planned Wasm-validated shape.
* **Explicit Plugin Orchestration:** The core Go compiler acts strictly as a neutral graph builder and never guesses how to process a node. Instead, all domain intelligence is explicitly orchestrated via dedicated WebAssembly (Wasm) sockets at two distinct levels.
  **1. Global Sockets:** Enterprise policies and formatting are evaluated by explicitly registered compiler sockets (e.g., `mutator.wasm` for metadata auto-tagging, `policy-validator.wasm` for topological security, and `renderer.wasm` for final artifact generation).
  **2. Implementation Pipelines:** Component-specific mutation logic is orchestrated by the `Manifest`; when it resolves an abstract interface to a concrete `Recipe`, that implementation explicitly declares a sequential `pipeline` array of Wasm plugins to execute. The compiler simply feeds the target-agnostic Intermediate Representation (IR) graph into these defined sockets, ensuring all domain-specific logic remains strictly versioned in the ecosystem rather than hardcoded into the core engine.
* **Flat Compilation & Feature Atomicity:** Aggrega does not manage state, ping endpoints, or pause for deployments. The compiler evaluates nested modules and resolves them down into a flat, 1-dimensional Intermediate Representation (IR) graph before passing the data to the Wasm rendering plugins. Crucially, while the graph is flattened, the compiler perfectly preserves **Feature Atomicity**. If a proxy feature autonomously declares a network edge to a secure vault, the compiler records the semantic origin of that edge, ensuring Wasm policy engines can execute $O(1)$ lookups without falsely attributing the connection to the parent component. Finally, to support temporal sequencing, each boundary in the Release carries a `syncWave: <integer>` value; rendering plugins translate the per-boundary wave into native execution-order annotations for the downstream GitOps controller.

### 4. **The Semantic Ontology: Identification & Taxonomy**

* **The 7-Type Cloud-Native Ontology (The Catalog Social Contract):** To ensure open-source Wasm plugins and corporate policies can interoperate universally, the ecosystem relies on a strict Social Contract. The `component.aggrega.ai/type` label maps exclusively to 7 universal cloud primitives (`server`, `worker`, `task`, `function`, `stateful-server`, `resource`, `messaging`). While the Go compiler is mathematically blind to these strings, establishing this baseline taxonomy guarantees that autonomous policy engines and community-built Wasm rendering plugins share a reliable vocabulary to determine how to provision the physical compute and network base.
* **Duck Typing (Semantic Traits via Labels):** If the base types are purely cloud-native, all cognitive, operational, and compliance intelligence is layered entirely through semantic duck-typing. Labels authored by the Platform Architect (e.g., `model.aggrega.ai/capability: generative`, `compliance.aggrega.ai/data-class: restricted`) act as the true identity of the node. Features bind dynamically to components based on these label selectors.

### 5. **Enterprise Governance: Schemas & Inheritance**

* **Strict API Partitioning & Enterprise Discoverability:** Following Kubernetes standards, all payload definitions uniformly reside within a `spec:` block. Resource identity, characteristic labeling, and explicit compiler instructions reside strictly in the `metadata:` block. To guarantee strict resolution, every shareable YAML artifact strictly mandates a Regex-enforced SemVer `version` string. Furthermore, to support OCI registry discoverability and lifecycle governance, the `metadata` block supports an optional **Enterprise Metadata Suite**. This suite includes `description`, a structured `maintainers` object array (name, email, url), `license`, `repository`, `home` (documentation URL), `keywords` (for search indexing), and a `deprecated` boolean flag to safely manage end-of-life components without breaking existing GitOps pipelines.
* **Schema Extensibility (The Kubernetes CRD Pattern):** To avoid updating the core compiler schema for every new AI or infrastructure feature, the platform uses **JSON Schema 2020-12** to validate configurations. Platform Architects write strict types, validation logic, and default values directly inside the Catalog components' `schema:` block — typically authored in compact form, a YAML-shaped shorthand that fits per-field constraints on one line (`port: { type: integer, min: 1, max: 65535, default: 8080 }`) and compiles to JSON Schema 2020-12 before validation runs. Full JSON Schema YAML remains a co-equal authoring option for schemas that need its complete vocabulary. Catalogs that grow large enough to benefit from cross-Component schema reuse pull common shapes (probe blocks, resource limits, named-port shapes) into a dedicated **SchemaLibrary** entity and reference them via the JSON Schema `$ref:` keyword.
* **Monotonic Schema Inheritance (Payload Baselines):** To enforce configuration standards, the platform splits inheritance into two distinct tiers. While standard YAML metadata (including semantic labels), `Manifest` mappings, and `Release` configurations utilize traditional merge strategies to allow necessary environment overrides, the actual payload schemas (`schema:`) compose under JSON Schema 2020-12 composition semantics. A custom merger with source-position provenance tagging walks the `extends:` chain at workspace load, producing a single merged schema with every leaf carrying its originating file. **Monotonic narrowing — a child can tighten a parent's constraint (shrink an enum, narrow a numeric range) but cannot relax it — moves from a language-level invariant to a publishing-policy-level enforcement.** The standard publishing-discipline Wasm linter rejects narrowing violations by default; per-workspace configuration (`enforce_monotonic_narrowing`, `narrowing_exemptions`) lets enterprises tune the rule per their compliance posture, and enterprises authoring their own publishing-linter plugin replace the default entirely. This guarantees an strong baseline for the application's payload when the standard policy ships unmodified, while properly delegating broader topological security and label governance to the Wasm policy sockets.
* **Interface Parity & Auto-Implementation:** To prevent Ops from duplicating Recipe YAMLs when an Architect spawns a slightly altered flavor of a Base Component, a planned extension will introduce Strict Implementation Completeness. Under the extension, the compiler will allow a Parent's Recipe to seamlessly implement a Child Component *if and only if* the Child did not introduce any *new* `usesSchema` sockets or new root keys to `values`/`infra`/`provides`. If the child expands the interface with new keys, the parent's template is inherently incapable of consuming them. The Tracker Struct pattern (emitting warnings when a rendering template does not read a provided variable, to prevent "Ghost Infrastructure") is the corresponding rendering-phase guardrail. When implemented, blocking mismatched keys at the resolution phase will guarantee the Recipe is structurally complete for the Child's contract before rendering begins.
* **`implements` Version Matching:** The `implements` field on Recipes and FeatureRecipes supports three forms to balance strictness with ecosystem flexibility:
    1. **Exact version:** `implements: "core/api-server:1.0.0"` — matches only `1.0.0`. For Recipes tightly coupled to a specific schema version.
    2. **Major-compatible (SemVer range):** `implements: "core/api-server:^1.0.0"` — matches `>=1.0.0, <2.0.0`. Designed for Recipes that ride the Component's SemVer compatibility guarantees: minor and patch bumps are assumed backward-compatible per SemVer, and the compiler extracts the major version and checks `recipe_major == component_major`. Range matching is a planned form; the compiler currently ships exact and unversioned matching only, so practical defaults today are exact-pinning (`core/api-server:1.0.0`) when a Recipe is tied to a specific schema version, or unversioned (`core/api-server`) when behaviour is version-agnostic.
    3. **Unversioned:** `implements: "core/api-server"` — matches any version. For Recipes that are genuinely version-agnostic (e.g., a generic worker Recipe that only uses `.context.inject.env` and no version-specific `values` fields).
  
  When the Manifest resolves a component to multiple candidate Recipes (e.g., one exact-versioned and one unversioned), the compiler picks the most specific match. If two candidates have equal specificity, the compiler halts with an ambiguity error. The compiler currently ships exact and unversioned forms; `^` range support is a planned extension.
  
  The three-form pattern lets Recipes declare the version contract that fits their actual coupling to the Component's schema. Recipes tightly bound to a specific schema version pin exactly; Recipes that ride the Component's SemVer compatibility guarantees use a major-compatible range; Recipes whose behavior does not depend on Component version at all stay unversioned. The result is that minor Component version bumps do not force Ops to either pin Component versions or maintain parallel Recipes per version.
