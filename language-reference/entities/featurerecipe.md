# FeatureRecipe

The conceptual role of the FeatureRecipe entity (Domain 3 — the Wasm-plugin-driven implementation of a Feature interface) lives in [architecture/04-eight-entity-taxonomy.md](../../architecture/04-eight-entity-taxonomy.md). This page covers the FeatureRecipe catalog authoring surface.

## Catalog Location

FeatureRecipes are organized with the provider as the namespace (same pattern as Recipes):

```text
aggrega-catalog/
└── feature-recipe/
    └── {provider}/                          # e.g., `helm`, `compose`, `eval`
        └── {feature-recipe-name}/
            └── recipe.yaml
```

OCI URI: `hub.aggrega.ai/feature-recipe/{provider}/{name}:{version}` (e.g., `hub.aggrega.ai/feature-recipe/helm/k8s-secret-from-parameter:1.0.0`).

## Authoring Contract

FeatureRecipes bind to a Feature interface via `implements` and declare a concrete provider. They support three distinct execution blocks — a superset of base Recipe authoring:

1. **`pipeline`:** A sequential array of WebAssembly (Wasm) plugins for Post-Render Workload Mutation (e.g., injecting an Envoy sidecar via JSONPatch, or mounting a secret volume). See [architecture/09-ai-features.md](../../architecture/09-ai-features.md) for the Two-Part Plugin Principle (Fetcher / Injector). **Status: accepted but inert** — the schema accepts the array shape but the compiler does not yet execute the plugins; see [Status of the Language](../10-status.md#compilation-pipeline-phases) for current behaviour.
2. **`source` & `valuesMapping`:** Used for Resource Generation, allowing Ops to render static templates natively (e.g., generating a new `HTTPRoute` CRD or an `ExternalSecret` CRD) alongside the base component.
3. **`injectMapping` (Pre-Render Interception):** A native Go template block executed *before* the Base Recipe renders. It outputs a JSON dictionary that the compiler natively deep-merges over the Caller's `.context.inject` memory pipe, allowing Wasm-free, Caller-Side mutation of environment variables and connection strings.

## `injectMapping` Exclusivity

The `injectMapping` field is **exclusive to FeatureRecipes** — it is intentionally absent from the base `Recipe` schema. This exclusivity isolates variable interception from `valuesMapping`: the Base Recipe's `valuesMapping` unknowingly consumes the rewritten `.context.inject` strings generated by FeatureRecipe `injectMapping` blocks, ensuring perfect decoupling. See the Phase-A Interception section below for how the mechanism runs, and [architecture/10-compilation-pipeline.md](../../architecture/10-compilation-pipeline.md) Phase A for the full pre-render interception semantics.

## Phase-A Interception: How `injectMapping` Works

When a caller needs the connection string to its target shaped differently than the target's unmodified `.provides.host` — appending a namespace for cross-boundary Kubernetes DNS, prefixing a region code for a multi-region gateway, or adding an SSL mode suffix to a DSN — `injectMapping` handles the mutation at the caller, before the base Recipe's `valuesMapping` ever sees the inject pipe.

The `injectMapping` field is a Go `text/template` that the renderer evaluates during Phase A of Step 5, before the base Recipe's Phase B rendering runs. The template outputs a JSON dictionary with optional mechanism keys (`env`, `file`, `arg`) — or a flat map which defaults to `env` — and the renderer deep-merges this overlay over the caller node's `.context.inject` pipe. Caller-side routing via `injectMapping` runs in Phase A without invoking a Wasm sandbox for simple string manipulation; Wasm plugins remain reserved for structural AST changes via the `pipeline` array.

**Mutation is strictly caller-local.** The FeatureRecipe modifies only the inject pipe of the node it is attached to, never the target's `.provides` output. A target's `.provides.host` is consumed by potentially many callers across the cluster; caller-side `injectMapping` merges only into the specific caller's pipe, so routing mutations stay scoped to the edge that requested them.

### Zero-coupling target inference

Because the compiler embeds each target's cascaded annotations into the caller's `.context.uses` pipe, the `injectMapping` template can extract routing coordinates without Ops hardcoding the target identity into the Feature's `infra`:

1. The template searches `.context.uses` to find the exact topological edge that injected the developer's requested variable.
2. It extracts the target's cascaded `release_annotations` (e.g., `aggrega.ai/namespace`).
3. It formats the Fully Qualified Domain Name (FQDN) or connection string.
4. It emits the override dictionary.

The compiler remains agnostic to the networking semantics — Kubernetes namespaces, cloud regions, bridge-proxy topologies — and simply executes the deep-merge with whatever the template produced. When the base Recipe's `valuesMapping` subsequently runs, it consumes the intercepted, rewritten strings from `.context.inject.env` as if they were the developer's originals.

### Worked example: K8s DNS resolver

Because environment variable names must be unique within a container, the `target_var` (e.g., `API_HOST`) acts as a globally unique identifier for a specific injection contract within the caller. By looping over the explicit edges in `.context.uses` and checking which edge claimed the `target_var`, the template locates the correct target node and extracts its cascaded annotations.

**The Routing Feature schema (`core/k8s-dns-resolver`):**

```yaml
infra: {
  target_var: string            # Ops dictates WHICH injected var to rewrite
  namespace_annotation?: string # Ops tells the feature WHERE to look for physical placement
}
```

**The FeatureRecipe implementation:**

```gotemplate
injectMapping: |
  # 1. Grab the atomic base host directly from the flattened pipe
  {{ $base_host := index .context.inject.env .infra.target_var }}
  
  # 2. Dynamically locate the specific edge that injected this variable
  {{ $target_edge := dict }}
  {{ range $alias, $edge := .context.uses }}
    {{ if hasKey $edge.inject.env $.infra.target_var }}
      {{ $target_edge = $edge }}
    {{ end }}
  {{ end }}
  
  # 3. Resolve the namespace using the annotation key provided by Ops
  {{ $ns := "" }}
  {{ if and .infra.namespace_annotation $target_edge }}
    {{ $ns = index $target_edge.annotations.release .infra.namespace_annotation }}
  {{ end }}

  # 4. Formulate the FQDN safely (fall back to the base host if no namespace exists)
  {{ $resolved_host := $base_host }}
  {{ if $ns }}
    {{ $resolved_host = printf "%s.%s" $base_host $ns }}
  {{ end }}

  # 5. Emit the precise override dictionary for the compiler to deep-merge
  env:
    "{{ .infra.target_var }}": "{{ $resolved_host }}"
```

## Use Cases Beyond Routing

`injectMapping` is most commonly used for cross-boundary address resolution (like the K8s DNS resolver above), but the Phase-A caller-side mutation applies to any scenario that requires intercepting and formatting developer intent before infrastructure rendering. Two further patterns illustrate the range.

**Dynamic security formatting (the SSL appender).** If an enterprise mandates that all external database connections use strict TLS verification, a Feature can intercept the developer's requested `DB_URL` and append the required SSL mode so the application boots with the correct security parameters.

```gotemplate
# Inside force-ssl-feature
injectMapping: |
  {{ $base_url := index .context.inject.env .infra.target_var }}
  env:
    "{{ .infra.target_var }}": "{{ $base_url }}?sslmode=verify-full"
```

**Multi-region gateway prefixing.** If a generic API component is deployed globally, a regional routing Feature can autonomously look up its own environment boundary annotations to prefix the injected connection strings for its callers.

```gotemplate
# Inside regional-router
injectMapping: |
  {{ $base_host := index .context.inject.env .infra.target_var }}
  {{ $region_code := index .context.annotations.release "cloud.aggrega.ai/region" }}
  env:
    "{{ .infra.target_var }}": "{{ $region_code }}.{{ $base_host }}"
```

**The boundary of `injectMapping`.** The mechanism is limited to mutating the `.context.inject` memory pipe (the Delivery Contract). It cannot append new containers, mount volumes, or alter the base Recipe's `valuesMapping` output. Any mutation that requires structural changes to the rendered AST (like JSON or YAML arrays) belongs in the FeatureRecipe's `pipeline` array, executed via WebAssembly plugins.

## Credential FeatureRecipe Pattern

When a FeatureRecipe implements a credential Feature (one labeled `feature.aggrega.ai/kind: secret`), it follows the Two-Part Plugin Principle: the `pipeline` chains a Fetcher plugin (generating the vault-specific CRD) followed by an Injector plugin (mounting the secret to the target container). See [examples/05-credential-features](../examples/05-credential-features.md) for the complete worked example with JSON input/output handshake.

## Provider & `implements`

The `provider` field is mandatory at the root level and declares which Wasm rendering plugin will execute the FeatureRecipe's output (`helm`, `compose`, `terraform`, `cloudformation`, `eval`, etc.). The `implements` field binds the FeatureRecipe to its Feature interface and supports exact, major-compatible range, or unversioned matching — see [vocabulary/inheritance-and-interface](../vocabulary/inheritance-and-interface.md) for `implements` Version Matching semantics.

## Execution Scope — `spec.executionScope`

The optional `spec.executionScope` enum selects the dispatch model for Resource Generation. Two values are accepted; the default when the field is omitted is `component`.

* **`component` (default).** The FeatureRecipe's Resource Generation runs once per attached component instance. Each invocation receives a per-component `TemplateContext` rooted at `.context.*` — `.context.instance_id`, `.context.inject`, `.context.uses`, `.context.annotations`, etc. — exactly as today. Existing FeatureRecipes that omit `executionScope` continue to behave identically.
* **`boundary`.** Resource Generation runs **once per attached boundary**, regardless of how many components inside the boundary's subtree consume the feature. Each invocation receives a boundary-scope `TemplateContext` rooted at `.boundary.*` instead of `.context.*`.

The Phase-A `injectMapping` mechanism (described above) is **always per-consumer** regardless of `executionScope`. Each component that uses the feature still gets its own caller-side rewrite of `.context.inject`. Only the Resource Generation step (`source`/`valuesMapping` and the `pipeline` array) deduplicates at boundary scope.

### Boundary-scope `TemplateContext`

When `executionScope: boundary`, the FeatureRecipe's templates evaluate against a `.boundary.*` view of the boundary the feature is attached to. The view exposes:

* `.boundary.path` — the boundary's evaluated `directory:` path (replaces `.context.instance_id`).
* `.boundary.boundary_name` — the boundary's authored name in the Release.
* `.boundary.components` — a map keyed by instance ID containing every component in the boundary's subtree (`instance_id`, `component`, `resolved_version`, `boundary_path`).
* `.boundary.internal_uses_edges` — `uses:` edges where both endpoints are inside this boundary's subtree.
* `.boundary.outgoing_cross_boundary_uses_edges` — edges with the source inside the subtree and the target outside (used by the compose-bridge pattern to enumerate connections that need a proxy).
* `.boundary.incoming_cross_boundary_uses_edges` — edges with the target inside the subtree and the source outside (used by ingress-style aggregators).
* `.boundary.cross_boundary_uses_edges` — the union of incoming and outgoing cross-boundary edges, when the FeatureRecipe wants the full cross-boundary view.
* `.boundary.labels` — the union of subtree labels with author-order preservation.
* `.boundary.annotations` — the boundary's own annotations plus the cascade.
* `.boundary.feature_attachments` — every feature attached at this boundary (so a boundary-scope FR can introspect siblings if needed).

The `.infra` pillar on a boundary-scope FR resolves to the **boundary-attached feature's** `infra:` block (Release-side authored physical sizing for that boundary attachment). `.values` is **always empty** for boundary-scope FRs: the Release schema's pillar-split rule forbids `values:` on Release-level Feature attachments, so a `BoundaryFeature` carries no values to project. Boundary-scope FRs that need parameter-shaped data should consume it via `.infra` (the operator's authoring surface for boundary-feature configuration), via `.boundary.annotations` (cascade-resolvable string values authored on the boundary or any ancestor), or via `.parameters.X` (Release-fulfilled typed parameters from the Aggregate's `parameters:` declaration). `.locals` continues to be the FR's own locals block. `.steps`, `.metadata`, `.parameters` remain unchanged.

### Boundary-scope template field allowlist

Boundary-scope FRs may only reference fields available in the boundary-scope view. Authoring a template that references a per-component-only field (e.g., `.context.instance_id`, `.context.inject`, `.context.uses`) when `executionScope: boundary` causes the FeatureRecipe to fail validation at parse time with an `FR_TEMPLATE_INVALID_FIELD` error naming the FR, the offending field, and the alternative fields available in the boundary-scope view. The mirror rule applies in the other direction: a component-scope FR that references `.boundary.*` fields fails the same validator.

The validator runs the same template-AST walk that the path-template variable allowlist uses, with a different reference set per scope.

### Deduplication and Resource Generation output

For `executionScope: boundary`, the compiler deduplicates Resource Generation by the tuple `(boundary_path, FR-instance)`. Two components in the same boundary subtree both consuming the same boundary-attached feature trigger one FR invocation, not two. Cross-boundary attachments of the same feature run independently per boundary.

A boundary-scope FR emits files under `<boundary_directory>/<fr-provider>/features/<feature-instance>/` for non-intermediate output (one set of files per `(boundary_path, FR-instance)` tuple). Intermediate output flows to the boundary's per-(path, provider) assembler at the FR's evaluated path under the FR's own `spec.provider` — this is the mechanism the compose-bridge proof case uses to merge a bridge service alongside per-component compose contributors at the same assembly path.

### Cascade-aware `provides:` resolution

Boundary-scope FRs produce one `provides:` set per `(boundary_path, FR-instance)` tuple. The FR's `provides:` template evaluates with the boundary-scope `TemplateContext` (so it can reference `.boundary.components`, `.boundary.path`, `.infra`, but not per-consumer fields and not `.values`). The provides values are **constants relative to consumers** — every consumer in the boundary's subtree sees the same provided values.

**Consumer-side resolution of boundary-scope FR provides is currently a deferred integration.** The `.context.uses.<feature-alias>.<provided-name>` surface resolves correctly for component-scope FRs as today; for boundary-scope FRs, the cascade walk from consumer to FR-attachment-bearing boundary is implemented as a helper but not yet wired into the consumer-side rehydration path. Boundary-scope FRs that need to expose values to consumers should currently rely on Phase-A `injectMapping` (which is per-consumer regardless of `executionScope` and works correctly today) rather than `provides:`. The cascade-aware provides path is expected to land when a use case requiring it surfaces.

### Compose-bridge proof case

The compose-bridge FeatureRecipe is the canonical boundary-scope-FR pattern. A `core/compose-bridge` feature is attached at a parent boundary that contains two sub-boundaries (e.g., `services-net` and `data-net` with shared `directory:`). The FR's `executionScope: boundary` ensures one bridge service is synthesized per parent-boundary attachment. Phase-A `injectMapping` rewrites each consumer's `DB_HOST` (or equivalent) to point at the bridge address. Phase-B Resource Generation emits the bridge's `nginx-stream` compose service, which the per-(path, provider) compose assembler merges with per-component compose contributors at the same evaluated path. The result is one `docker-compose.yaml` containing every component plus the bridge service, with cross-network routing wired correctly.

## The `assertions:` block

`FeatureRecipe.spec.assertions:` is an optional Go template body that expresses **implementation invariants of the FeatureRecipe** — cross-field rules that hold given the specific Wasm plugin pipeline, chart, or mechanism the FeatureRecipe wraps. Like Recipe assertions, FeatureRecipe assertions are properties of the specific implementation; the Feature-level contract rules apply independently at an earlier pipeline phase.

```yaml
spec:
  implements: core/secret-value:^1.0.0
  pipeline:
    - id: fetch-secret
      plugin: secret-providers/aws-secrets-manager:^1.0.0
  assertions: |
    {{- /* aws-secrets-manager plugin 1.x requires explicit region when no AWS_DEFAULT_REGION
           is implied through the Aggregate's infra block */ -}}
    {{- if not .values.region -}}
      {{- if not .infra.aws.region -}}
        {{- fail "aws-secrets-manager plugin 1.x requires either values.region or infra.aws.region to be set" -}}
      {{- end -}}
    {{- end -}}
```

The rule above is specific to the `aws-secrets-manager` plugin 1.x; it does not apply if a different `core/secret-value` FeatureRecipe binds. The Feature-level contract rules from the Feature definition still apply alongside.

FeatureRecipe assertions evaluate after FeatureRecipe binding and before Resource Generation. The template context for component-scope FRs mirrors the Recipe assertions context (entity-instance fields plus `.provides`, `.locals`, `.recipe.metadata`, `.recipe.source`); for boundary-scope FRs (`executionScope: boundary`), assertions evaluate against the boundary-scope view (`.boundary.*` fields available; per-component fields not). For the full authoring grammar and worked examples, see [templates/assertions-block.md](../templates/assertions-block.md).
