# Output composition

A single Aggrega build produces output files into per-boundary directories under `dist/` through six distinct mechanisms — sourced rendering, workload synthesis, FeatureRecipe Resource Generation, FeatureRecipe Phase C pipeline patches, Release-level composition, and direct artifact emission. The mechanisms run in a defined order; outputs collide deterministically when two mechanisms produce a file with the same name in the same boundary directory; the build halts before emission with a `CATALOG_ERROR:` naming every contributor when a collision is detected.

This page documents the six mechanisms in one place, names the rendering order across them, and consolidates the collision-detection rules previously scattered across [architecture/10-compilation-pipeline.md](../../architecture/10-compilation-pipeline.md), [architecture/16-recipe-input-composition.md](../../architecture/16-recipe-input-composition.md), and the per-entity Recipe / FeatureRecipe references.

## The six output-producing mechanisms

Each mechanism lives at a specific Recipe / FeatureRecipe authoring surface and produces files under specific naming conventions. The mechanisms accumulate per node — a single component instance can drive multiple mechanisms at once (a sourced base Recipe + a Workload-synthesised companion file + a FeatureRecipe-emitted ExternalSecret CRD + a Phase C patch applied to the synthesised Deployment).

### 1 — Recipe sourced rendering (`source:` + `valuesMapping:`)

**Authoring surface.** Recipe declares `source: <path>` plus `valuesMapping:` (the field accepts inline Go template, file `$import:`, or library `$import:` to a MappingLibrary entry — see [`entities/recipe.md`](../entities/recipe.md) "The `valuesMapping` field — three authoring modes"). The source points at an on-disk Helm chart, a docker-compose YAML file, or another provider-native artefact.

**Pipeline placement.** Step 5 Phase B, after the Recipe's locals + provides resolve.

**Output shape.** Provider-engine-specific:

- **helm provider** — flat Kubernetes YAML files, named `<nodeID>-<basename>.yaml` per chart-template emission. The Helm SDK renders the chart with the merged values; Aggrega injects provenance labels post-render.
- **helm-chart provider** — sub-chart files copied verbatim under `charts/<instance_id>/`; per-boundary umbrella `Chart.yaml` + `values.yaml` emitted alongside.
- **compose provider** — intermediate `<nodeID>.compose-fragment.yaml` files that flow into Release-level composition (mechanism 5).

### 2 — Recipe Workload synthesis (`workload:`)

**Authoring surface.** Recipe declares `workload:` carrying a Workload document. The field accepts inline content (block scalar) or `$import:` (file path) per the unified file-import vocabulary.

**Pipeline placement.** Step 5 Phase B, after the Recipe's valuesMapping resolves (the Workload body is itself a Go-templated string evaluated with full TemplateContext).

**Output shape.** Provider-engine-specific:

- **helm provider** — one Deployment (or StatefulSet when persistentTemplate volumes exist) + per-service Service + per-persistent-volume PVC. Files named `<nodeID>-<kind>.yaml` (e.g., `<nodeID>-deployment.yaml`, `<nodeID>-service-<svcName>.yaml`, `<nodeID>-pvc-<volName>.yaml`).
- **compose provider** — intermediate `<nodeID>.compose-fragment.yaml` files that flow into Release-level composition.
- **helm-chart provider** — not supported; helm-chart's role is sourced-mode chart composition only. A Recipe targeting helm-chart with `workload:` is rejected at Recipe load.

### 3 — FeatureRecipe Resource Generation (sourced mode for FeatureRecipes)

**Authoring surface.** FeatureRecipe declares `source:` plus `valuesMapping:` (or equivalent), same pattern as Recipe sourced rendering but for Feature attachments rather than primary Components.

**Pipeline placement.** Step 5 Phase B, alongside the base Recipe rendering for the parent Component. Each Feature attachment runs its own FeatureRecipe rendering pass.

**Output shape.** Files emitted into the same boundary directory as the parent Component's output, typically named `<nodeID>-<feature-instance-id>-<resource>.yaml`. Common shapes:

- An `ExternalSecret` / `VaultSecret` CRD generated by a credential FeatureRecipe's Fetcher.
- A `ServiceMonitor` / `PrometheusRule` CRD generated by an observability Feature.
- An `HTTPRoute` / `Gateway` CRD generated by a routing Feature.

### 4 — FeatureRecipe Phase C plugin pipeline (Strategic Merge Patch + Resource Generation)

**Authoring surface.** FeatureRecipe declares `pipeline:` — an array of Wasm plugin steps (Two-Part Plugin Principle: Fetcher + Injector for credential Features; arbitrary plugin pipelines for non-credential Features).

**Pipeline placement.** Step 5 Phase C, after Phase B base + FeatureRecipe sourced rendering completes.

**Output shape.** Plugin-specific. The architectural design covers two output classes:

- **Strategic Merge Patches** that the host applies to the parent Component's rendered AST (e.g., appending a sidecar container, mounting a secret volume, rewriting an env var on the synthesised Deployment).
- **Resource Generation** — full new resources emitted alongside the patch (typically the Fetcher's vault-fetch CRD that the Injector then references).

**Status today:** Phase C runtime is `accepted but inert` per [Status of the Language → Compilation pipeline phases](../10-status.md#compilation-pipeline-phases). The schema accepts `pipeline:` declarations; the Wazero runtime that would execute the plugins is not yet wired. See [`wasm/plugin-contract.md`](../wasm/plugin-contract.md) for the plugin contract surface.

### 5 — Release-level composition (per-provider Boundary Composer)

**Authoring surface.** Driven by the Release shape — no per-Recipe authoring. The compose provider's `BoundaryComposer` aggregates all per-node fragments into one `docker-compose.yaml` per boundary; the helm-chart provider's `BoundaryComposer` aggregates per-node sub-chart copies into one umbrella chart per boundary.

**Pipeline placement.** Post-Phase B, after every node's per-Recipe output has accumulated for the boundary.

**Output shape.** Per-provider:

- **compose provider** — one `docker-compose.yaml` at the boundary root, aggregating every contributing node's services, volumes, and networks. The intermediate `<nodeID>.compose-fragment.yaml` files (mechanisms 1 + 2) are merged into the single output; the fragments do not appear in the final boundary directory.
- **helm-chart provider** — one umbrella `Chart.yaml` + `values.yaml` at the boundary root, plus per-node sub-chart directories under `charts/<instance_id>/`.

### 6 — Recipe direct artifact emission (`artifacts:`)

**Authoring surface.** Recipe declares `artifacts:` as a map of named entries; each entry is either inline content (a templated string carrying the file body) or an `$import:` reference to a template file path — direct file emission without going through a provider engine.

**Pipeline placement.** Step 5 Phase B.3.

**Output shape.** One file per artifact entry, named per the entry's key in the `artifacts:` map. The Recipe author dictates filename and content directly.

**Status today:** **`accepted but blocked`** per [Status of the Language → Recipe input kinds](../10-status.md#recipe-input-kinds). The schema accepts `artifacts:` declarations; the Phase B.3 evaluator returns a `CATALOG_ERROR:` naming the field as not yet implemented. Recipes that declare this field halt the build until the implementation ships.

## Rendering order

The six mechanisms run in a defined order so downstream mechanisms can read upstream outputs. The order:

1. **Phase B preamble** — Recipe `locals:` evaluate; provides templates evaluate (Pass 1).
2. **Phase B.0** — Recipe `source:` URI templates evaluate (resolving the source pointer if templated).
3. **Phase A** — FeatureRecipe `injectMapping:` blocks evaluate (the inject pipe is intercepted before Recipe rendering).
4. **Phase B.1** — Recipe `valuesMapping:` evaluates (sourced mode + sourceless mode produce values dictionaries).
5. **Phase B.2** — Recipe Workload synthesis (mechanism 2 emits manifests for synthesised mode).
6. **Phase B.3** — Recipe `artifacts:` evaluation (mechanism 6 — `accepted but blocked` today).
7. **Phase B.4** — Provider engine renders (mechanism 1 — sourced mode produces flat manifests; sourceless mode produces generative manifests).
8. **Phase B.5** — FeatureRecipe rendering for every Feature attachment on the node (mechanisms 3 + 4 — Resource Generation runs at sub-Phase B.5; Phase C plugin pipeline runs at sub-Phase C if and when wired).
9. **Phase C** — Post-render mutation: FeatureRecipe `pipeline:` plugin steps apply Strategic Merge Patches and emit additional resources (mechanism 4 — `accepted but inert` today).
10. **Release-level composition** — per-provider `BoundaryComposer` aggregates per-node fragments into per-boundary outputs (mechanism 5).

The order matters because downstream mechanisms can read upstream outputs — for example, a Phase C plugin can patch a Phase B.4-rendered Deployment; a Release-level composer can merge fragments emitted by Phase B.4 + Phase B.5 + Phase C.

## Collision-detection rule set

When two mechanisms produce a file with the same name in the same boundary directory, the build halts with a `CATALOG_ERROR:` naming every contributor. The rule set:

### Recipe shape rule 6 — `artifacts:` entry-key collision

A Recipe declares two entries under `artifacts:` with the same key (the key dictates the emitted filename, whether the entry's body is authored inline or loaded via `$import:`). Detected at Recipe load time per [`errors/fatal-halts.md`](../errors/fatal-halts.md) Recipe shape rule 6.

### Recipe shape rule 7 — Cross-input-kind emission-time collision

A Recipe's three input kinds — sourced, synthesized, and artifacts — each emit files into the same boundary directory. If source-rendered, workload-synthesized, or artifact-emitted output produces a file whose name another input kind also produced, the build halts at emission. Detected at Phase B.5 emit time per [`errors/fatal-halts.md`](../errors/fatal-halts.md) Recipe shape rule 7.

### Compose service-name collision (Release-level)

When two different nodes (in any combination of boundaries) contribute services with the same name to the merged compose output, the compose provider's `BoundaryComposer` halts with a `TRANSLATION_ERROR:` naming every contributing `(boundary, node, serviceName)` tuple. Detected at Release-level composition per [`providers/compose.md`](../providers/compose.md) Release-level output section.

### Helm-chart sub-chart alias collision

When two component instances declare the same instance ID (after sanitisation) in the same boundary, the helm-chart provider's `BoundaryComposer` would write both sub-charts under the same `charts/<alias>/` path. The collision is structurally prevented today — instance IDs are unique per boundary by Aggregate-flattening rules — but the aliasing convention surfaces the boundary explicitly.

### Helm rendered-resource name collision

Within a boundary, two nodes that render to the same Kubernetes resource name (e.g., two Deployments named `api-server`) produce two YAML files with overlapping `metadata.name` fields. The helm provider does not detect this at render time today — the file names differ (`<nodeID>-deployment.yaml` for each node, with different `<nodeID>`) but the `metadata.name` inside each file may collide. Kubernetes rejects the apply at runtime; the collision surfaces post-Aggrega rather than at the build.

The naming convention `<nodeID>-<kind>.yaml` plus the synthesised Service-name convention `<nodeID>-<svcName>` (per [`entities/workload.md`](../entities/workload.md) "Synthesised-name convention") makes cross-node collisions structurally impossible by construction. Authors who hit a runtime K8s rejection on a Deployment / Service name should look first at whether two different Recipes are emitting same-named resources via different rendering paths (e.g., a sourced chart's `templates/deployment.yaml` colliding with a workload-synthesised Deployment's `metadata.name`).

## Cross-mechanism interaction patterns

### Workload-synthesised + Phase C patch

The canonical pattern: mechanism 2 (workload synthesis) emits a base Deployment; mechanism 4 (Phase C Injector plugin) applies a Strategic Merge Patch that mounts a secret volume into the Deployment. The two mechanisms compose — the Deployment is the same K8s resource, with the patch layering ConfigMap / Secret references onto the synthesised base.

When Phase C ships, this is the dominant pattern for credential injection on synthesised workloads. The Fetcher (mechanism 3, Resource Generation) emits an `ExternalSecret` CRD that the cluster fetches at runtime; the Injector (mechanism 4, Phase C patch) modifies the Deployment to mount the resulting K8s Secret.

### Sourced + Workload synthesis on different boundaries

A single Aggregate can have one component bound to a sourced helm Recipe (mechanism 1) on boundary A and a sibling component bound to a Workload-synthesising helm Recipe (mechanism 2) on boundary B. Each boundary's directory carries the appropriate output shape; cross-boundary file naming does not collide because per-boundary `dist/` directories are sibling-isolated.

### Compose Release-level merge across boundaries

The compose provider's `BoundaryComposer` is unusual — it aggregates per-node fragments not just within one boundary but across every compose-targeted boundary in the Release into a **single** `docker-compose.yaml`. This is the canonical compose shape (one compose file per project); the per-boundary fragmentation is intermediate state.

Service-name collisions across boundaries are therefore real and detected at the Release-level merge per the rule above. Two compose-targeted boundaries that each declare a service named `api` collide unless the boundaries are isolated (different Releases, different `dist/` directories).
